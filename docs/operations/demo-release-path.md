# Demo service release path

This walkthrough connects the sample workload to DeployForge's release contract. It prepares the source files and provider configuration; it does not publish them or start a cluster deployment.

## Flow

```text
DeployForge API
  -> durable build run in the database
  -> worker dispatches workflow_dispatch
  -> GitHub Actions builds an immutable image tag in GHCR
  -> Grype scans the image and Syft creates a CycloneDX SBOM
  -> Cosign signs the image digest; GitHub attests SLSA provenance and SBOM
  -> runner writes the digest to the deployforge/staging GitOps branch
  -> runner sends source and manifest revisions in an HMAC-authenticated callback
  -> DeployForge verifies signature/provenance and applies policy gates
  -> operator approval and exact-revision Argo CD sync happen through the control plane
```

The API does not keep an HTTP request open while the workflow runs. The database-backed worker owns dispatch, callback deadlines, retries, and release state. A runner reports only the immutable image digest and evidence generated by that workflow.

## Provider prerequisites

Before enabling a release:

1. Publish the project to `sahadatx/DeployForge` and require review plus status checks on `main`. The staging workflow accepts only protected `main` so the generated manifest branch cannot combine an older tagged source with newer staging configuration. Allow the workflow's repository-scoped `GITHUB_TOKEN` to write the generated `deployforge/staging` branch, prohibit force pushes, and restrict updates to the trusted release workflow.
2. Configure DeployForge's GitHub Actions token, workflow path, callback secret, and runner-reachable HTTPS callback base URL as described in [the GitHub Actions integration guide](../integrations/github-actions.md).
3. Add the same callback secret to the GitHub repository as `DEPLOYFORGE_CALLBACK_SECRET`, and set repository variable `DEPLOYFORGE_CALLBACK_ALLOWED_HOST` to the public API hostname. Keep the secret in the repository secret store and rotate it with the DeployForge API setting.
4. Make the GHCR package writable by the workflow's `GITHUB_TOKEN`. For production cryptographic verification with the current Sigstore public trust configuration, use a public GitHub repository; GitHub uses a separate private Sigstore instance for private repositories.
5. Configure Argo CD and a restricted `platform` AppProject. The repository URL, target cluster, namespace, and application name must match the DeployForge GitOps target.

GitHub-hosted runners cannot reach `localhost` on the developer's computer. A release callback needs an HTTPS endpoint reachable by GitHub; the local API at `http://localhost:8000` is not one. Do not expose the local API directly to the internet to work around this.

## Image digest and GitOps manifest binding

The source branch deliberately keeps a zero-digest placeholder. After every successful scan, signature, and attestation step, the release workflow merges the requested source commit into `deployforge/staging`, replaces the image placeholder with the built image's immutable SHA-256 digest, and pushes that generated manifest revision. The Argo CD Application tracks this branch. DeployForge stores the source commit and GitOps manifest commit separately, then asks Argo CD to sync the exact manifest commit:

```yaml
images:
  - name: deployforge-demo-service
    newName: ghcr.io/sahadatx/deployforge-demo-service
    digest: sha256:<verified-64-character-image-digest>
```

The placeholder cannot identify a real image, so the main branch alone is not deployable to staging. The generated branch keeps the desired image digest reviewable and reproducible in Git. The Argo CD Application remains manual-sync; promotion still passes through DeployForge's policy and approval gates, and it is only reported successful when Argo CD observes that exact manifest revision as `Synced` and `Healthy`. Protect the generated branch against force pushes and restrict who can update it; the release workflow must be allowed to merge the protected source revision and push the digest update.

## Local development

The local Compose demo remains independent of GitHub and Kubernetes:

```sh
docker compose -f examples/demo-service/compose.yaml up --build -d
```

Use `http://localhost:8090/health/ready` to see its readiness response. It does not create a GitHub build run, signed artifact, or Argo CD deployment record.

## Expected release evidence

The workflow reports:

- GHCR OCI image URI pinned by its SHA-256 digest.
- CycloneDX SBOM digest and vulnerability counts from the Grype report.
- Cosign Sigstore image-signature bundle.
- GitHub-generated SLSA provenance bundle, bound to the source repository and commit.
- Immutable GitOps manifest revision containing the same image digest.
- GitHub Actions run URL for review and audit navigation.

If scanning, signing, attestation, or callback delivery fails, the run reports failure. A successful callback is accepted only after DeployForge independently verifies the cryptographic bundles when verified supply-chain mode is enabled.
